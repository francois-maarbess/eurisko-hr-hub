# ADR-002: Password accounts and single-company scope (SSO deferred)

## Status

Accepted

## Context

The product spec describes company SSO and a multi-tenant platform. The
Academy track explicitly scopes those out: one company, localhost, no
enterprise authentication, no phone app. The Week-3 mock login (email only,
no credentials) cannot remain: a launch needs real accounts, and "admin
inviting users" is the documented real-company flow.

## Decision

1. **Passwords, not SSO.** `passwordHash` (nullable) on User, verified with
   `bcryptjs` — pure JavaScript, same API as bcrypt, zero native toolchain
   (the Week-3 `better-sqlite3` saga proved native deps are a liability here).
   Admins create accounts with an initial password; users sign in with
   email + password. Unknown users, wrong passwords, inactive and
   passwordless accounts all return the same 401 (no account enumeration).
2. **Single company, membership scoping instead of tenancy.** There is no
   `companyId` anywhere: request lists are scoped by person (`mine` default),
   department membership (queue), or claimant. One person may serve several
   departments (spec §12). No tenant middleware is needed at this scale.
3. **Sign-out is server-revoked.** Refresh tokens are opaque, hashed at rest,
   single-use with rotation in the `RefreshToken` table; logout revokes the
   whole family, and reusing a rotated token kills every session (theft
   signal). Access JWTs stay short-lived (15m) and stateless.
4. **SSO stays deferred**, not deleted: the schema and flows accept a future
   identity provider without rework (email stays the stable identifier).

## Consequences

- Instructors can create, log in as, deactivate, and reassign any demo
  account from the Administration panel — no seed editing.
- Request views are personal by default; the shared queue is a staff
  privilege, which matches least-privilege (architecture.md).
- If SSO ever arrives, only the login step changes; memberships, roles,
  and request rules are identity-agnostic.
