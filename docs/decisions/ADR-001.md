# ADR-001: Isolate Document Payloads in Object Storage

## 1. Context
The Internal Operations Service Hub requires storing user-uploaded HR documents (primarily PDFs) alongside request metadata. Relational databases (PostgreSQL) are optimized for structured text, indexing, and strict state machines. Embedding heavy binary files directly into database rows causes severe I/O bottlenecks, massive database bloat, and makes compute scaling unnecessarily expensive.

## 2. Decision
We will store all document payloads in an isolated, private Object Storage bucket. The PostgreSQL database will strictly store the structured metadata and a text-based reference URL (`document_url`) pointing to the bucket location.

## 3. Consequences
* **Positive:** Database read/write performance remains lightning-fast, and storage scales cheaply and independently of the compute instance.
* **Negative:** Introduces data synchronization complexity. If a file upload fails mid-flight, or if an HR admin deletes a document, the backend must execute multi-step logic to ensure the Object Storage and the database do not end up out of sync (orphan files or dead links).
