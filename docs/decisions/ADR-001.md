# ADR-001: Store document payloads in private object storage

## Status

Accepted

## Context

Requests may contain PDFs or other approved documents. Binary payloads do not belong in relational rows: they increase database size, slow backups and queries, and complicate scaling. Documents also require stricter access controls and an independent retention lifecycle.

## Decision

Store document bytes in a private, encrypted object-storage bucket. Store only metadata and an opaque storage key in the relational database. All uploads, downloads, deletions, and purge operations are brokered by the API.

The API must validate size, MIME type, extension, and content signature before accepting an upload. Public URLs and client-side storage credentials are prohibited.

## Consequences

### Benefits

* Database remains focused on structured data and transactional state.
* Storage can scale independently and enforce lifecycle expiration.
* API authorization is applied consistently to every document operation.

### Costs and mitigations

* Database and storage can become inconsistent during failures. Use transactional metadata updates, idempotent object operations, checksums, reconciliation jobs, and alerts.
* Downloads add API bandwidth. Stream authorized downloads and apply endpoint rate limits.
* Purged documents remain visible in audit history but are no longer downloadable. Record `deleted_at` and the purge result explicitly.
